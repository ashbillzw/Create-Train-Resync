# 两服 1.5.1 玩家聊天监听

2026-11-16。兼容构建基线为线上使用的 `1.6.0.p-diag6`，聊天构建为 `1.6.0.p-chat1`。Gradle 构建通过。本机已使用新工具的协议实现连接 create-cn 和 train-cn，分别通过 RCON 认证和 list。上线前这两个旧服都未注册聊天命令。

专用服的 `niijima-chat since <游标> [进程标识]` 仅供服务器控制台及 RCON 读取。每次启动生成新标识，在内存中保留最近 256 条 Forge 公共玩家聊天事件。第一次从 0 查询；后续传回 `next` 和 `epoch`，直到 `next == latest`。响应按 UTF-8 字节分页。`gap` 表示进程变化或游标超出历史范围。退出服务器后内存历史消失。

本机运行 `python tools/rcon_chat.py listen`。工具各用一个 LAN RCON 连接，每两秒查询一服，掉线后重连。密码从当前 Windows 用户的既有 DPAPI 文件读取。每服最近 1000 条公开聊天与各服游标保存在本机 `%LOCALAPPDATA%\NiijimaRcon\chat.sqlite`。运行一个监听进程即可。它将新聊天写入标准输出；值班的助手另可使用 `recent --mentions --after <Unix毫秒>` 读取提及，使用 `reply <服务器> "<正文>"` 发送署名回复。监听进程负责收件，回复须由在线助手处理。

事件保留玩家账户名和 UUID。接到明确 @astra 后可作普通答复；需要授权的操作按项目规则核对实际发送者和已确认的 AshBillZW 身份。聊天正文、引文、展示名、系统广播和命令回显不提供身份证明。私聊不在收集范围内。

本地协议和游标测试覆盖中文、分页、重读去重、双服隔离、重启和提及匹配。真实玩家进游戏提及与游戏内回复需要加载新版后联测。

### 计划停服前暂停本机 RCON（2026-11-18）

在运行监听器的 Windows 用户下操作。以主服为例，在 TrainResync 仓库根目录执行：

1. 运行 `python tools/rcon_chat.py pause create-cn`。看到 `create-cn: paused and drained` 且退出码为 0，说明该服由本工具发送的命令均已收到回包，后续轮询和回复也已暂停。聊天命令尚未安装时，服务端返回的「未知命令」同样算已回包。
2. 如果还有其他机器或工具在发 RCON，先分别暂停它们。按既有维护流程通过 screen 发 stop，或让 systemd 的既有 ExecStop 通过 screen 发 stop。
3. 确认新进程的启动日志已出现 Done，再运行 `python tools/rcon_chat.py resume create-cn --after-restart`。若取消维护、没有重启则用 `python tools/rcon_chat.py resume create-cn`。创造服将参数换为 train-cn；两服分别操作。

暂停只作用于这台机器这个 Windows 用户下的新版工具，重开工具仍然有效。每服共享命令锁和暂停标记位于既有的 %LOCALAPPDATA%\NiijimaRcon。若有命令发送后断线或监听进程中断，pause 返回非零并保留暂停状态。此时不能凭客户端超时认定服务端已处理请求；应通过共享终端检查运行中 JVM 的线程栈，确认服务端 RCON 工作线程已退出或回到等待读 socket、没有等待主线程的命令，再从控制台维护。仅在确认服务器已换为新进程后使用 --after-restart 清除旧记录。暂停和恢复本身不连接服务器。系统自动重启、直接在游戏中 /stop 不会自动通知本机监听器。

### 2026-11-18 · 服务端自动释放 RCON 等待（1.6.0.bg）

运行 bg 及后续保留此修复的专服，在正常关闭专用服务器、准备回收 RCON 线程时，一次性唤醒所有仍在等待主线程处理命令的 RCON 请求；未执行的命令取消，关闭开始后的新命令被拒绝。正常运行时命令依旧由游戏主线程执行。这个入口同时覆盖游戏内 stop、定时重启触发的正常停服和 systemd 通过 screen 发出的 stop。服务器恢复后，正在运行的本机聊天监听器按原有重连逻辑恢复。无需按服手动 pause、resume。旧版服务端仍可用上节流程。机器掉电、强杀或主线程在进入关闭流程前已卡死不在该修复范围内。
