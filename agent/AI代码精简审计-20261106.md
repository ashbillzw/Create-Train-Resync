## 优先考虑的精简

### A1 合并四份完全相同的厨具热源 Mixin

位置为 mixin/cauldron/cookery/ 下 PotBlockEntityMixin、SteamerBlockEntityMixin、StockpotBlockEntityMixin、TeapotBlockEntityMixin，各 18 行，实际注入在 12–17 行。

四个文件仅目标类型及类名不同，都重定向 hasHeatSource 中同一 Level.getBlockState 调用，并返回 HeatSources.view。四者同属 kaleidoscope_cookery 可选加载组，均无 Shadow 或独有状态。

可用一个多目标 @Mixin 保留同一个 handler，将四条注册缩为一条。项目已有 LightMovingInteractionMixin 的双目标和 LeashableTagMixin 的多目标实例可参考。预计四文件 72 行变成约 21–24 行，净减约 48–51 个物理行，具体以实现后统计为准。

落地应核对四个目标方法的实例/static 形式及注入匹配均成立，保持原加载条件。不要将方法名或侧别不同的其他热源 Mixin 一起硬合并。

### A2 合并两份相同的发射器入口 Mixin

位置为 mixin/cauldron/CauldronDispenserBehaviorMixin.java:12–18 和 FillFluidHolderBehaviorMixin.java:13–19。

两者都在 customBehavior 的 HEAD 调用 CauldronContainers.dispense，并且仅在结果非 null 时替换原方法返回值。其参数、返回类型、注入策略与加载条件一致。

可合为一个双目标 Mixin，移除一份文件及注册。两文件共 39 行，预计净减约 17–18 个物理行。必须保留 null 放行原生行为的语义。

A1、A2 最适合作为第一批，合计可减少 4 个源文件、约 65–69 个物理行，业务分支无需改写。这些数量是静态估计，未构建验证。

### A3 统一创建液体锅的流程

位置为 compat/cauldron/MilkIntegration.java:35–76，重点为 49–53 和 70–74。

fillAt 的映射流体分支与 fillContentAt 重复检查世界、识别空锅、计算接受量、区分模拟与执行、创建同一 Amendments 方块并取回 MilkAccess。以后改变建锅失败处理需要同步两处。

最小改法是提取“实际创建锅并取得 MilkAccess”这段操作，复用现有填充计算。若进一步合并整条流程，应保留流体身份判定和最终写入方式的差异，避免为了去重引入多个回调或通用策略框架。

尤其要保持模拟操作不创建方块、-1 交还原始管道路径、0 表示已接管但拒绝，以及映射流体的 NBT 一致性检查。不能只用字符串 type 相同替代 isFluidEqual。

### A4 用调用内共享变量替换合成过程的静态 ThreadLocal

位置为 mixin/cauldron/CommonCauldronCodeMixin.java:51–60、64–118、127–152。

inputs、position、arrowRemaining 三个 ThreadLocal 只是为同一次合成的多个注入点传数据，需要手动在入口、分支与 RETURN 清理。这里的复杂度主要来自跨钩子状态管理。

position 可以像该类 handArrows 已有写法一样捕获调用者参数。inputs 与 arrowRemaining 可评估用已有 MixinExtras @Share/LocalRef 保存，LiquidCauldronBlockMixin:34–48 已在同项目使用 @Share。

这能减少静态共享状态和 remove 调用，且调用递归时更容易界定生命周期。手持与掉落物两个目标方法要各自使用独立调用上下文，保留逐个物品回退、冷却标记和药箭剩余精确容量。应验证取消、异常与嵌套调用路径，不能仅删掉清理代码。本条为需要编译及针对性验证的候选。

### A5 集中 MilkTankMixin 中的接纳规则与排液写回

位置为 mixin/cauldron/MilkTankMixin.java:93–108、110–131、133–145。

fill 与 isFluidValid 分别写了同样的普通流体／映射流体接纳判断。两个 drain 重载也重复读取库存、构造结果、设置数量，以及在 EXECUTE 时扣除库存。

适合提取小范围的流体匹配判断，以及“已确定取出量后的结果与扣量”操作。SIMULATE 不写状态、已移除实体拒绝访问、返回原生实现的条件，以及带 NBT 的映射流体比较都必须保留。普通 drain 与按类型 drain 的匹配约束不同，不宜直接删除其中一个。

收益是容量与 NBT 规则集中维护，预计减行有限，不值得扩大成一套新容器框架。

### A6 比较器数值计算已有共享入口，另一钩子仍复制公式

位置为 mixin/cauldron/ModCauldronBlockMixin.java:16–23，对照 compat/cauldron/CauldronSignals.java:24–28，以及 mixin/cauldron/BlockStateBaseMixin.java:29–33。

ModCauldronBlockMixin 重复“精确容量优先，否则按层数”的同一算法。可在核对接收 state 确属目标方块的正常调用条件后，委托现有 CauldronSignals.signal。

保留两个入口是否必要需看依赖调用方式。外部可能直接调用 Block 的比较器方法，因此不能仅因 BlockState 层已有拦截就删除整个 Mixin。共享计算即可减少维护点。

## 小型清理与注释

### B1 复用原版 Items 常量，避免为比较物品创建 ItemStack

compat/cauldron/CauldronDrops.java:59–61 用 MilkIntegration.item("minecraft:glass_bottle").getItem() 和同样的 bowl 写法判定物品。它每次都解析资源 ID、查表并构造临时物品栈。

直接使用 Items.GLASS_BOTTLE、Items.BOWL 更清楚，已有 import 可用。这是上次审计曾提出、当前 main 仍存在的残留项。运行频率依赖掉落物接触，未做性能测量，不宣称加速比例。

### B2 洗涤预览重复构造结果

compat/cauldron/CauldronCrafting.java:18–20、41–44 中，canWash 调 washed 得到非 null 后丢弃，craft 立即再次调用 washed。一次合成可能重复复制物品、清除颜色或编辑旗帜 NBT。

在 craft 内保留一次预览结果，并复用到结果构造。canWash 仍有外部用途，不能因该处去重就直接删去。收益以减少复制和表达清楚为主，不承诺明显减行。

### B3 冰淇淋口味识别有两份规则

compat/cauldron/MilkIntegration.java:132–137 和 compat/cauldron/MilkConversions.java:19–25 都遍历相同口味；后者为比较物品还逐次构造 ItemStack。

可在 CauldronContents 中保留一个明确的口味识别函数，由手持预测和实际转换使用。需要减少重复计算时传递已识别结果，但不要让客户端预测调用有副作用的 apply。满锅要求、奶酪优先级、创造模式及掉落物消耗各有用途。

### B4 注释不是主要体积来源

按行首 //、/*、* 的简易统计，main 生产源码 AI 归属中仅有 82 行纯注释样式行，约占上述物理行的 2.3%；这是粗计数，不是 Java 语法级统计。

明确可缩的是 compat/cauldron/CauldronContents.java:11–13 中用户日期、HARDCODED 和三句历史说明。可改为“固定口味清单，新增项须同步软流体资源”，决策历史保留在专题。TrainResyncMixinPlugin.java:55 的默认 fallback 说明也可随实际维护压缩。

以下注释说明不直观的约束，应保留含义：Gzip 必须读至 EOF、原子保存不得清理失败临时文件、跨维度碰撞缓存、清洗与投料副作用，以及可选依赖的类加载边界。
