## 1.6.0.p-diag2 · 堆快照看门狗宽限（2026-11-05，仅诊断分支）

分支 diag/railway-memory-20261104，基于已上线 p-diag；没有合入 main 上后续的 q 版修复与精简。本次在 RailwayWatchdogMixin 增加 22 行，其他生产代码不变。

专服工作目录存在普通文件 `trainresync-heap-dump.flag` 时，仅将 ServerWatchdog 单次 tick 的超时判定门槛设为 300,000 毫秒（总计五分钟，非额外五分钟）。文件内容不读取，不自动创建或删除；无标记时使用原有 max-tick-time。标记长期残留仍会使后续 tick 使用五分钟门槛，不代表关闭看门狗，也不是创建文件五分钟后自动失效的计时器。

超时比较与休眠分开：原版仍按常规门槛计算唤醒时间；诊断模式下若休眠不足一秒（包括已超过常规门槛导致的负值），改为一秒后复查。保留本轮是否处于诊断模式的快照，避免标记在比较与休眠之间移除后，负休眠令看门狗线程异常退出。未新增线程、配置项、命令或采集功能。

操作顺序为：启动已加载此 JAR 的 JVM → 在对应实例工作目录创建标记 → 采集堆快照 → 确认服务器 tick 已恢复推进 → 删除标记。不要仅凭 jcmd 返回就立即删除，因为看门狗可能先于游戏主线程恢复执行。移除后在下一轮看门狗检查恢复原门槛。两服标记彼此独立；不得将诊断标记打包分发。

用户澄清：DAT 的“决定退出后等保存”与快照的“判定超时前放宽门槛”保持独立。实际超过五分钟仍进入原版崩溃／退出流程，此时若仍有 DAT 保存，原有最多额外五分钟等待继续生效；本次没有为满足退出墙钟总时长而取消 DAT 保护。整 JVM 暂停期间无法保证 Java 看门狗准时执行，五分钟不是外部强制终止采集的硬截止。外部 mc-watchdog-r2 不受此 Mixin 控制。
